## Findings

**F1 — `bundleFormat`: the two sides give different answers for the same document, and the hub's
assumption is not visible where its own code says it should be.** THE HUB'S, and nothing is broken
today.
- The served document carries **no `bundleFormat` key at all** (checked with `'bundleFormat' in doc`;
  its top-level keys are `id, name, description, appVersion, baseMapVersion, distanceUnit,
  unitIsPrefix, temporal, mapMode, invertDisplay, scale, systems, routes, broadcastId`).
- The **engine** reads such a document as **0** — `takeBundleFormat`, `src/lib/io/bundle.ts`:
  *"Returns 0 for a file written before the stamp existed — legacy, never an error."*
- The **hub** base-stamps it to the `legacy_bundle_format` gate and publishes **`bundleFormat: 1`** on
  `/api/maps/local-neighbourhood`, flat, with nothing saying it was assumed.
- The hub already intends otherwise. `gateAgainstKnown` returns `{ ok: true, format, legacyStamped }`
  and the comment above it says the assumption is *"Flagged so the assumption stays visible in the
  database rather than becoming invisible the moment it is made."* But `ingest.ts:461` writes only
  `bundle_format: format`, the schema is `bundle_format integer not null` (0001_init.sql:84) with no
  column for the flag, and `api/maps/[slug]/+server.ts:38` exposes the bare integer. **`legacyStamped`
  is computed and dropped.**
- **Why it will matter later rather than now:** while `BUNDLE_FORMAT` is 1 the assumed value and the
  true value coincide. On the day it becomes 2, "unstamped" and "format 1" stop being the same claim,
  and the record will not distinguish them. A column or an API field, not a redesign.

**F2 — R-01's stamp has never round-tripped through the hub.** The only map in the library was made
with engine **3.0.190**, before the plain-JSON stamp shipped, so the hub's format gate has only ever
seen its legacy path. The stamped path is unexercised end to end. Worth one upload of a
currently-saved map to close.

**F3 — engine, cosmetic, and not this stream's to fix.** Commit `6952ef80`'s subject reads
`v3.0.321` while its `package.json` and `static/shipped-content.json` both read `3.0.322` — a subject
left stale after a rebase. The tree is consistent and beta serves 3.0.322; only the record misleads,
and amending pushed history would be worse than the blemish.

**F4 — a latent trap, recorded so nobody re-derives it.** The engine's allow-list **does** accept
`explorers.starsystemx.com` (verified: `isTrustedOpenUrl` returns null for it). So if `site_url` were
ever set to that host before the DNS moves, every link would build a download URL that 404s and the
engine would report *"Could not reach the map library"* — a network-shaped message for a
configuration-shaped fault. Both halves have recorded not to; this is why.
