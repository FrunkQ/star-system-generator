## 1. N-1.4's FIRST clause — "with no campaign the map opens straight away" — was not in the other run, and it PASSES

The primary report marks criterion 4 PASS on four behaviours: a campaign present, accepting, a refused host,
and the parameter. **The clause the brief opens with, and the one the hub's half named as "NOT verified, and it
is N-1's", is the no-campaign path** — and it is the one behaviour that cannot be seen in any browser that has
already opened a map. It was run here on a virgin origin (a dev server at the same commit beta serves,
`localhost:5344` at 6952ef80), with `indexedDB.databases()` and `localStorage` both confirmed EMPTY immediately
before the click.

**Seen:** the map opened with **no replace question at all**, the notice read `Opened "Local Neighbourhood"
from the shared map library.` — **without** the "your previous campaign is one step back" clause the other run
saw — **no `pre_upgrade_starmap` was written**, and `location.search` was empty afterwards.

**And the precondition is real rather than contrived:** merely loading the app creates nothing. A first load of
`/` left IndexedDB absent and localStorage at zero keys, so "no campaign in the browser" is the state an actual
first-time visitor arrives in, not a state manufactured for the test. That is worth recording because the
engine's decision is exactly `if ($starmapStore || hasSavedStarmap)` (`src/routes/+page.svelte:977`), and a
reader could reasonably have assumed the app seeds a campaign on first run, which would have made the
straight-through path unreachable in practice. It does not, and it is reachable.

## 2. A correction owed to the HUB's half of R-13, and it strengthens their conclusion

The hub's `docs/sse-requirements.md` explains the null result under R-13 with *"`temporal_registry` is empty
since B112"*. **The library's only map is not empty.** Measured directly in the served document:
`temporal.temporal_registry` carries **all four** shipped calendars (`Earth Gregorian`, `Star Trek Stardate`,
`Mayan Haab (Simplified)`, `Chinese Lunisolar (Simplified)`) and `coiCategories` carries **all nine** shipped
categories.

Both statements reconcile through [[B112]] itself: B112 shipped the delta at v3.0.225 so NEW saves carry only
the GM's own, but `local-neighbourhood` was written by **SSE 3.0.190**, long before it — and B112's row already
records that a delta cannot know what an older build shipped. So the hub's conclusion holds for a better reason
than the one written down: the facets are absent not because the file is empty but because **the baseline
absorbs the four and the nine that are genuinely in it.** That is R-13 doing the job it was asked for, on the
only real file available, rather than a no-op on an empty container.

Verified the same way in both directions: running the hub's own `applyFacetRules` over the served document with
`shipped = null` **skips** the two baseline facets rather than reporting four custom calendars and nine custom
categories — the stated fallback, measured on a real file instead of a fixture.

## 3. `appAssetPrefixes` has no visible consumer today — a hub finding, not an engine one

R-13's asset half exists to replace the hub's hand-rolled path matching. It is wired
(`isAppAsset`, `src/lib/bundle/shipped.ts:102`) and it is CORRECT — but `appArtwork` is incremented in
`src/lib/bundle/facets.ts:99` and then **neither persisted nor rendered anywhere**. `carried_images` is written
to the row at ingest and re-index; `appArtwork` is not, and no map page displays an app-vs-GM verdict for an
image at all. **This is why N-3.2's third clause ("a map page classifies an app star image … as app content and
a GM's own upload as the GM's") cannot be answered by looking at a page**, independently of the other run's
reason that the one map predates the wiring.

So the classification was exercised directly instead, over the real 334,708-byte document and the live manifest:

| input | with the live manifest | with NO manifest (the old prefix rule) |
| --- | --- | --- |
| `/images/star_types/G.webp` (60 of these in the document) | app artwork | app artwork |
| `/models/nasa/voyager.glb` | app artwork | app artwork |
| `assets/images/abc123.png` (a GM's upload) | the GM's | the GM's |
| `/images/ui/logo.svg` (app chrome) | **NOT app artwork** | **app artwork** |

The last row is `appAssetPrefixes` earning its place in one line: it gets a case right that the fallback guess
gets wrong. It is also the case nobody can currently see the answer to.

## 4. One more corroboration of N-3.1's version equality

Beyond `appVersion` matching `package.json` on the deployed commit, the running app's own
`localStorage['tag-categories']` holds **exactly the manifest's thirteen category ids, in the same order** —
an independent sign that the manifest is generated from the app's real sources rather than maintained beside
them. (The hub's deleted copy had nine; the four it lacked were `frontier`, `anomaly`, `science`, `intrigue`.)
